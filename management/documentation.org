#+DATE: <2026-08-10 Mon>
#+STARTUP: overview

This document is a living tutorial. Read it top to bottom once, then come
back to each section as you touch the code. It starts from zero
(syntax) and climbs to this exact website's architecture.

The site is a *personal dashboard + blog*:
- Dashboard: cards showing the status of self-hosted services (Forgejo,
  Syncthing, Email).
- Blog: your Emacs =notes= (org files) that are tagged =#+public: t=,
  read live from the server and rendered in the browser.

Stack: React + TypeScript + Vite + Tailwind v4 (Catppuccin Mocha) on the
frontend; a tiny Node.js server (h3) that serves the built files and a
few =/api= endpoints.

* Part 0 — How the web works (the 20-minute version)

** The request/response loop
Every time your browser loads a page it sends an HTTP *request* to a
server and the server sends back an HTTP *response*.

#+begin_example
browser --- GET /blog ---> server (node)
browser <--- HTML file --- server
#+end_example

HTTP is just text with rules. The most important pieces:
- *Method*: what you want to do. =GET= = read. =POST= = send data.
- *Path*: what you want. =/blog=, =/api/notes=.
- *Status code*: how it went. =200= OK, =404= not found, =500= server error.

Try it yourself:
#+begin_src sh
  curl -I https://lunixose.duckdns.org/
  curl https://lunixose.duckdns.org/api/services/forgejo
#+end_src

** The three languages of the browser
- *HTML*: the skeleton / structure of a page.
- *CSS*: the appearance (colors, spacing, fonts).
- *JavaScript*: the behavior (reacting to clicks, fetching data).

** Where your code runs
- *Server-side*: code that runs on the machine hosting the site. In this
  project that's =server/= (Node.js). It reads your org files and talks
  to service APIs, because it holds secrets and can reach internal
  networks.
- *Client-side*: code that runs in the visitor's browser. In this project
  that's =src/= (React). It renders the UI and shows the data the server
  sends.

This split is the single most important idea in the whole site. When you
see "why is this in =server/= and not =src/=?", the answer is almost
always: secrets / CORS / file access.

* Part 1 — JavaScript + TypeScript essentials

We use TypeScript, which is JavaScript plus types. The browser runs
JavaScript; TypeScript is *compiled* to JavaScript by Vite before the
browser sees it. Types catch mistakes while you type instead of at
runtime.

** Variables and types
#+begin_src ts
  let count: number = 1            // a number
  const title: string = "hello"    // a string (const = never reassign)
  const tags: string[] = ["nix", "linux"]   // array of strings
  const isPublic: boolean = true   // boolean
#+end_src

Rules of thumb:
- Prefer =const= unless you must reassign.
- TypeScript infers types a lot: =const x = 3= is already a =number=.

** Objects and interfaces
#+begin_src ts
  interface Note {
    id: string
    title: string
    tags: string[]
    date: string
  }

  const note: Note = { id: "20260810T131614", title: "hello website", tags: ["test"], date: "2026-08-10" }
#+end_src

An =interface= is a contract: "an object with this shape". If you forget
=tags=, TypeScript complains before you ever run it. See
=src/lib/types.ts= for the site's contracts.

** Functions
#+begin_src ts
  function add(a: number, b: number): number {
    return a + b
  }
#+end_src

Arrow functions are the modern style:
#+begin_src ts
  const add = (a: number, b: number): number => a + b
#+end_src

** Async and fetch (this one is everywhere)
Reading from a server takes time, so the browser does it in the
background. =async/await= is the syntax for "wait for this".

#+begin_src ts
  async function loadNotes(): Promise<Note[]> {
    const res = await fetch("/api/notes")     // send GET, wait
    if (!res.ok) throw new Error(`HTTP ${res.status}`)
    return res.json()                          // parse JSON body
  }
#+end_src

- =await= pauses the function until the network finishes.
- =Promise<Note[]>= declares what the function will eventually produce.
- See =src/lib/api.ts= — this is the site's real fetch helper.

* Part 2 — React mental model

React is a library for building UIs by declaring what the screen *should
look like* for a given state, and it figures out how to make the DOM
match.

** Components
A component is just a function that returns JSX (HTML-looking markup).

#+begin_src tsx
  function Greeting(props: { name: string }) {
    return <h1>Hello, {props.name}</h1>
  }
#+end_src

** Props
Inputs to a component. The parent passes them like HTML attributes:
#+begin_src tsx
  <Greeting name="lunixose" />
#+end_src

Props flow *down*. A component cannot change its own props.

** State
Data a component owns that can change. When state changes, React
re-runs the component and updates the DOM.

#+begin_src tsx
  import { useState } from "react"

  function Counter() {
    const [count, setCount] = useState(0)   // [current value, setter]
    return (
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>
    )
  }
#+end_src

=useState= returns a pair: the value and a function to change it. Never
mutate the value directly; always go through the setter, or React won't
know to re-render. See =useTheme= and =useWidgetStatus= in =src/hooks=.

** Effects
=useEffect= runs code *after* the component renders, which is where
side-effects live (fetching data, subscribing to events).

#+begin_src tsx
  import { useEffect, useState } from "react"

  function Notes() {
    const [notes, setNotes] = useState<Note[]>([])

    useEffect(() => {
      fetch("/api/notes").then((r) => r.json()).then(setNotes)
    }, [])   // empty array = run once when the component mounts

    return <ul>{notes.map((n) => <li key={n.id}>{n.title}</li>)}</ul>
  }
#+end_src

The second argument (the dependency array) controls *when* it runs:
- =[]= → once on mount.
- =[notes]= → every time =notes= changes.
- nothing → every render (usually a bug).

** Custom hooks
A hook is a function that uses React hooks, so you can reuse logic.
=useWidgetStatus= wraps the whole "fetch a status, track loading/error"
loop so each widget card gets it for free.

* Part 3 — Vite and the build pipeline

Vite is the *bundler*. It takes all your =src/= files, compiles
TypeScript → JavaScript, CSS → browser CSS, and bundles React + your code
into a few optimized files in =dist/=.

- =npm run dev= → start a fast dev server with hot reload (=localhost:5173=).
- =npm run build:web= → compile everything into =dist/=.
- =npm run build:server= → bundle the Node server into =dist-server/index.mjs=.
- =npm run build= → both.
- =npm run preview= → run the real server against =dist/=.

The =vite.config.ts= dev proxy forwards =/api/*= to the Node server so
the browser can call it during development without CORS errors (see Part 4).

* Part 4 — Why widgets go through the server (CORS + secrets)

The browser will happily call =https://git.lunixose.duckdns.org/api/v1/...=
for Forgejo — but Forgejo's API needs a token, and tokens in browser JS
are readable by anyone (view source). Also, cross-origin requests are
blocked by the *same-origin policy* unless the server sends CORS headers.

So the pattern is: the browser calls our own server (=/api/services/forgejo=),
and the server calls Forgejo with the secret token. The browser only
ever talks to us. This is called a *proxy*.

The plan =server/utils/forgejo.ts= and =server/utils/syncthing.ts= will
hold these proxies. The Syncthing token will live in a service env
variable on the server, never in the frontend bundle.

* Part 5 — The org pipeline (Emacs notes → blog)

Your notes are Denote-style files:
#+begin_example
20260810T131614--hello-website__test.org
#+end_example
=YYYYMMDDTHHMMSS--title__tags.org= — the filename encodes date, title,
and tags. Inside each file, org keywords add more metadata:
#+begin_example
#+title: hello website
#+filetags:  :test:
#+public: t
#+end_example

** Reading them
The server scans =/root/Notes=, reads filenames + the =#+= lines, and
keeps only notes with =#+public: t=. It exposes the result as JSON via
=GET /api/notes=. No per-post deployment, no commits — the blog updates
whenever Syncthing syncs a new note.

** Rendering them
The raw org text is served via =GET /api/notes/:id=. The browser turns
it into HTML using =uniorg= (an org parser for JS) inside the
=PostView= component. Org → headings/paragraphs/bold etc. becomes normal
HTML, styled with Catppuccin.

Why client-side instead of server-side? The org → HTML step is pure
computation with no secrets, so doing it in the browser keeps the server
thin and teaches the React render flow. TOC and reading time are
computed from the same parsed structure.

** Known pitfalls (documented so we remember)
- =uniorg= output is a tree (AST) that must be converted to HTML; the
  pipeline is uniorg-parse → uniorg-rehype → rehype-stringify. All three
  packages are installed. Wrapping them in a hook (=useOrgToHtml=) will
  centralize this.
- Headings need =id= attributes for the TOC anchors to jump anywhere.
  The org parser does not add them; we must inject =id= + slugs.
- Very large org files → large HTML; the TOC should be limited in depth.
- Note ids come from filenames, which are unique by construction.

* Part 6 — The deploy (Nix + Caddy)

The site runs as a NixOS systemd service =lunatix-website= on the VPS:
- =website.nix= defines the service: runs =node index.mjs=, sets
  =NOTES_DIR=/root/Notes=, opens port 3100, sets up ACLs so the =www-data=
  user can read your notes.
- =caddy.nix= defines =lunixose.duckdns.org= which reverse-proxies
  incoming HTTPS traffic to =127.0.0.1:3100=.

The website repo is a flake input of the =lunatix= repo. Deploy loop:
1. Push changes to the website repo.
2. In lunatix: =nix flake lock --update-input website= (new commit hash).
3. Commit the =flake.lock=, push lunatix.
4. SSH to the VPS and run =nixos-rebuild switch= with the new flake.

Nix builds the site (compiles =dist/= + =dist-server/=), installs it into
the Nix store, and systemd restarts the service. That is why
=nix/package.nix= must match what =npm run build= produces.

* Glossary (jump in anytime)

- *DOM*: the browser's in-memory tree of HTML elements; JS manipulates it.
- *JSX*: HTML-like syntax inside TypeScript that React turns into DOM calls.
- *Hook*: a React function that gives components superpowers (=useState=,
  =useEffect=). Custom hooks let you reuse that logic.
- *AST*: Abstract Syntax Tree — structured data representing parsed text.
  uniorg produces one from your org files.
- *CORS*: a browser security rule blocking cross-origin requests unless the
  server explicitly allows them.
- *Proxy*: our server calling another service on the browser's behalf.
- *SSG / SSR*: static site generation (build once) vs server-side rendering
  (compute per request). This site is a React SPA: the server sends the
  shell once, the browser renders everything after.
